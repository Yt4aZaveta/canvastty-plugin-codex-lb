# Codex LB Limits for CanvasTTY

A CanvasTTY HOME widget that shows each codex-lb account's remaining 5-hour and longer quota windows. It uses codex-lb's [`GET /api/fleet/summary`](https://github.com/Soju06/codex-lb/blob/main/app/modules/fleet/api.py) endpoint.

## Requirements

- CanvasTTY 1.7.0 with runtime plugin support.
- A local codex-lb with a CORS proxy, or a remote codex-lb behind an HTTPS reverse proxy with CORS configured as described below. Remote connections do not require local Docker or Caddy.
- A codex-lb API key with the `upstream_limits` and `account_pool_usage` usage sections. The codex-lb setting that hides upstream quota from API keys must be off.

## Local connection (Docker Compose example)

The included [compose.yaml](compose.yaml) starts codex-lb and Caddy. It expects an external Docker network and volume named `codex-lb-net` and `codex-lb-data`, so an existing codex-lb data volume can be reused. Clone this repository, create the network and volume only if they do not already exist, then start the stack:

```sh
git clone https://github.com/Yt4aZaveta/canvastty-plugin-codex-lb.git
cd canvastty-plugin-codex-lb
docker network create codex-lb-net
docker volume create codex-lb-data
docker compose up -d
```

If the network or volume already exists, skip its `create` command. The example publishes codex-lb's ports `2455` and `1455` on the host; Caddy listens only on `127.0.0.1:2456`. Caddy forwards `GET /api/fleet/summary` to `codex-lb:2455` on the Docker network and answers the CORS preflight from CanvasTTY's sandboxed widget. The API key passes through Caddy in the request header and is not stored there.

Use `http://127.0.0.1:2456` as the base URL on the same computer as CanvasTTY. This is also the default when no URL has been saved, so existing installations keep using their saved API key and local endpoint. HTTP is allowed only for `localhost` and `127.0.0.1`.

## Remote connection over HTTPS

Expose codex-lb through an HTTPS reverse proxy with a certificate trusted by CanvasTTY. Enter its base URL in the plugin settings, for example `https://lb.example.com` or `https://example.com/codex-lb/`. The plugin appends `/api/fleet/summary` while preserving an optional path prefix:

```text
https://lb.example.com          → https://lb.example.com/api/fleet/summary
https://example.com/codex-lb/    → https://example.com/codex-lb/api/fleet/summary
```

Use the final API location: authenticated requests reject redirects. URLs containing a username/password, query parameters, fragments, or the full summary endpoint are rejected before saving. A failed remote connection does not switch back to localhost.

CanvasTTY's plugin iframe has an opaque origin (`Origin: null`). The remote reverse proxy must accept `OPTIONS` preflight and `GET` on the summary endpoint and provide:

```http
Access-Control-Allow-Origin: null
Access-Control-Allow-Methods: GET
Access-Control-Allow-Headers: Authorization
```

The CORS headers must also be present on unsuccessful GET responses, including authorization failures, so the widget can report their HTTP status. The proxy must forward the `Authorization` header to codex-lb. The plugin sends `GET` with Bearer authentication, omits cookies and disables caching. TLS verification remains enabled.

The following is a **separate remote Caddy example**, not a replacement for the repository's local [Caddyfile](Caddyfile) or [compose.yaml](compose.yaml). It assumes the remote proxy can reach `codex-lb:2455`, DNS points `lb.example.com` to that proxy, and Caddy can obtain a trusted HTTPS certificate. Deferred headers cover responses from codex-lb, including errors; `handle_errors` adds the same headers to errors generated by the proxy:

```caddyfile
lb.example.com {
    @preflight {
        path /api/fleet/summary
        method OPTIONS
    }
    @summary {
        path /api/fleet/summary
        method GET
    }
    header /api/fleet/summary {
        Access-Control-Allow-Origin "null"
        Access-Control-Allow-Methods "GET"
        Access-Control-Allow-Headers "Authorization"
        defer
    }
    handle @preflight {
        respond "" 204
    }
    handle @summary {
        reverse_proxy codex-lb:2455
    }
    handle {
        respond "Not Found" 404
    }
    handle_errors {
        header /api/fleet/summary {
            Access-Control-Allow-Origin "null"
            Access-Control-Allow-Methods "GET"
            Access-Control-Allow-Headers "Authorization"
        }
        respond "Proxy error" {http.error.status_code}
    }
}
```

For a base URL with a prefix, expose the corresponding prefixed summary path and remove that prefix before forwarding to codex-lb. Keep the same CORS handling. The HTTPS summary endpoint is sufficient for the widget; it does not need remote server management routes.

## Install in CanvasTTY

1. Open **Settings → Plugins**.
2. Paste `https://github.com/Yt4aZaveta/canvastty-plugin-codex-lb` and choose **Inspect**. Review the manifest and the `network`, `secrets` and `storage` permissions, then confirm **Install**. CanvasTTY installs the ready-to-run files from this public repository; local Docker Compose, if used, is started separately.
3. The HOME widget is added automatically when there is room. If it is not visible, add **Codex LB limits** under **Settings → Appearance → HOME composition**.
4. Open the plugin's **Settings** action in **Settings → Plugins**, or click the HOME widget's **⚙** button. Both open the same settings page.
5. Enter the base URL and codex-lb API key, then click **Сохранить** (or press Enter). The base URL is stored through `host.storage`; the API key remains only in `host.secrets` under its existing name, `codex-lb-api-key`. The page restores the saved URL, never displays the saved key, and shows save progress, success or errors. A key is required on first setup; after a key has been saved, leaving the key field empty keeps it unchanged.

Typing does not trigger requests to the new URL. After a successful save, an already-open widget reloads the URL and key through the storage change event, including when only the key changed. No Disable/Enable is needed for configuration changes. Previous data is cleared and an old in-flight response cannot restore it after a server change.

To update, open **Settings → Plugins**, choose **Check for updates**, then click **Update** for this plugin. If the HOME widget was already open, **Disable** and then **Enable** this plugin in the same section to reload its iframe with the new files. This keeps the plugin installed and its saved key.

The widget follows CanvasTTY's selected `sage`, `lilac`, or `night` palette through the plugin context, including changes while it is open. CanvasTTY's plugin context does not expose the separate HOME accent preset.

The widget reads persisted quota snapshots on opening and once a minute. Its refresh button rereads those snapshots; it does not call codex-lb's upstream refresh route. Missing quota data is shown as unknown, not as 0%.

Requests time out after 15 seconds. The widget reports authorization errors (401/403), other HTTP failures, invalid response formats, timeouts and general network failures separately. Browser fetch cannot reliably distinguish CORS failures from other connection or TLS failures; check the selected server and its reverse proxy when a network error appears. If an update fails without a configuration change, any displayed data is labelled as the last received snapshot.

## Manual checks after installing the changed files

- With an existing saved key and no saved URL, open the widget and confirm it still reads the local `127.0.0.1:2456` endpoint.
- Open settings from the plugin card and from the widget's gear. Save a URL, reopen the page, and confirm that URL is restored and the saved key stays hidden.
- Connect to an HTTPS server with correct CORS, including a path prefix if used. Change only the URL with the key field empty, then change only the key. Confirm the open widget updates without re-enabling the plugin.
- Switch servers while the old request is delayed. Confirm old accounts disappear immediately and the delayed response cannot replace the new server's data.
- Try a credentialed URL, remote HTTP, a query, a fragment and the full summary path. Confirm errors appear and the saved configuration does not change. On first setup, also try an empty key.
- Check denied storage/secrets access, HTTP 401/403 and 500, invalid JSON or missing `accounts`, an unreachable server, a delayed response and a redirect. Confirm visible errors, no secret values in messages, and that a timed-out request can be refreshed again.

## Package layout

```text
canvastty.plugin.json   CanvasTTY manifest v1
config.js               Shared URL validation and configuration keys
widget/                 Static HTML, CSS and JavaScript
settings/               Static canvas-app settings page
compose.yaml             codex-lb and Caddy services
Caddyfile                CORS for the fleet summary endpoint
bridge/bridge.py         Legacy standalone bridge
```

The manifest stays at the repository root, as supported by CanvasTTY's [runtime plugin format](https://github.com/howdeploy/CanvasTTY/blob/main/docs/plugins.md). No build step is required.
